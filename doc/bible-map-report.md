## 1. 자료의 원천 (세 갈래)

이 프로젝트는 **아무것도 창작하지 않았습니다.** 세 개의 이미 존재하는 자료를 엮은 것입니다. 어떤 자료를 어디서 가져왔는지 분명히 아는 것이 이런 작업의 절반입니다.

### 1-1. 사건의 뼈대 — 노션 「사복음서 조화표」

꿈골이 직접 정리해 둔 노션 데이터베이스 「예수님의 행적을 기준으로 한 사복음서 대조」입니다.

- 248행, 8국면(A~H), 약 239개 사건
- 각 행의 열: `번호` · `마태복음` · `마가복음` · `누가복음` · `요한복음`

이 표가 **사건의 순서와 구분에 대한 유일한 기준**입니다. 사건을 임의로 쪼개거나 합치지 않았고, 국면 구분도 그대로 따랐습니다. 「예수님의 생애를 몇 개 사건으로 볼 것인가」는 학자마다 다른 해석의 문제인데, 이미 정리된 자기 표를 기준으로 삼으면 그 논쟁에 발을 들이지 않고도 일관성을 얻습니다.

MCP(Model Context Protocol)의 노션 연결을 통해 SQL로 읽어 왔습니다.

```sql
SELECT "번호","마태복음","마가복음","누가복음","요한복음"
FROM   collection://a66e8899-f1ad-42e0-b1a5-96f11095f201
WHERE  "번호" LIKE 'D-%'
```

> **교훈** — 자료를 화면에서 복사·붙여넣기로 옮기면 반드시 오타가 생기고, 원본이 바뀌었을 때 추적할 수 없습니다. 기계가 읽을 수 있는 경로(API·MCP·CSV)를 먼저 찾으세요.

### 1-2. 성경 본문 — 로컬 SQLite 성경 DB

암송 구절과 연결 구절의 **본문 전체**는 `~/Desktop/Data/BibleDB/`의 개역개정 DB에서 꺼냅니다. 절대로 기억에 의존해 타이핑하지 않습니다.

```python
def verse(ref: str) -> str:
    """개역개정 본문을 볼트의 성경 DB에서 가져온다(암기·연결 구절용)."""
    out = subprocess.run(
        ["python3", str(VAULT / "scripts/bible_db.py"), "quote", "개역개정", ref],
        capture_output=True, text=True, cwd=str(VAULT)).stdout.splitlines()
    ...
```

관찰·해석 단계의 **참조 구절**은 본문을 싣지 않고 대한성서공회 공식 페이지로 링크합니다. 저작권 문제를 피하면서 독자가 늘 최신·정확한 본문을 보게 하는 방법입니다.

```python
def bible_url(ref: str) -> str | None:
    m = re.match(r"^([가-힣]+)\s*(\d+):(\d+)", str(ref))
    code = BOOKCODE.get(m.group(1))          # 마→mat, 막→mrk, 눅→luk, 요→jhn …
    return ("https://www.bskorea.or.kr/bible/korbibReadpage.php"
            f"?version=GAE&book={code}&chap={m.group(2)}&sec={m.group(3)}")
```

> **교훈** — 성경, 찬송가, 시(詩)처럼 **정확한 인용이 신뢰의 근거인 자료**는 기계가 읽을 수 있는 원본을 갖추고 거기서만 꺼내야 합니다. 「대충 맞는 인용」은 인용이 아닙니다.

### 왜 지도를 Hugo 페이지가 아니라 `static/`의 독립 HTML로 만들었나

| 이유 | 설명 |
|---|---|
| **테마 충돌 회피** | Blowfish 테마의 CSS·JS가 SVG 확대/이동 코드와 부딪히지 않습니다. |
| **전체화면 가능** | 파일 자체가 완결되어 있어 `target="_blank"`로 그냥 열립니다. |
| **재사용** | 교재 78과가 같은 지도 코드를 미니지도로 재활용합니다. |
| **디버깅 용이** | 브라우저에서 파일 하나만 열면 됩니다. Hugo를 거치지 않습니다. |

임베드는 자체 shortcode 한 줄로 합니다.

```go-html-template
{{/* layouts/shortcodes/mapframe.html */}}
{{- $src := .Get "src" -}}
{{- $h := .Get "height" | default "80vh" -}}
<div class="mapframe" style="…height:{{ $h }};min-height:520px;…">
  <iframe src="{{ $src }}" loading="lazy" title="성경지도 인터랙티브 지도" …></iframe>
</div>
```

## 3. 핵심 기술 ① 지도 좌표 — 「위경도를 픽셀로」

지도 작업의 90%는 좌표 문제입니다. **점을 눈대중으로 찍으면 반드시 지리적으로 틀립니다**(→ [이슈 1](#이슈-1-지도가-지리적으로-틀림-★가장-중요★)).

### 3-1. 지역 지도 — 투영이 EPSG:4326이라 계산이 선형이다

`Southern Levant blank topographic map`은 **평사도법(plate carrée, EPSG:4326)** 으로 그려져 있습니다. 이 투영에서는 위경도가 픽셀에 **정비례**합니다. 원본 SVG의 격자선에서 값을 읽어 두 줄로 정리했습니다.

```python
# 원본 viewBox 2000×2500, 경도 33~37, 위도 29~34  →  1도 = 500px
def sx(lon): return 500.0 + (lon - 34.0) * 500.0
def sy(lat): return 500.0 + (33.0 - lat) * 500.0
```

> 위도는 북쪽이 클수록 화면에서는 **위**(y가 작음)이므로 `33 - lat`로 뒤집습니다. 이 부호를 놓치면 지도가 남북으로 뒤집힙니다.

### 3-2. `Frame` — 원본의 일부만 잘라 쓰기

국면마다 무대가 다릅니다. 갈릴리 국면은 호수 주변, 유대 국면은 예루살렘 근방입니다. 원본 전체를 보여 주면 사건이 좁쌀처럼 뭉치므로, **원본의 사각형 일부를 잘라 1000×680 캔버스에 채웁니다.**

```python
class Frame:
    """원본 지형도의 일부를 잘라 1000x680 캔버스에 맞춘다."""
    def __init__(self, cx0, cy0, cw):
        self.cx0, self.cy0, self.cw = cx0, cy0, cw
        self.ch = cw * H / W          # 캔버스 비율(0.68)을 그대로 유지
        self.s  = W / cw              # 확대 배율

    def px(self, lat, lon): return (sx(lon) - self.cx0) * self.s
    def py(self, lat, lon): return (sy(lat) - self.cy0) * self.s
```

배경은 SVG 안에서 **외부 SVG를 `<image>`로 불러** 같은 배율로 늘립니다.

```python
bgx, bgy = (BG_VB[0] - fr.cx0) * fr.s, (BG_VB[1] - fr.cy0) * fr.s
bgw, bgh = BG_VB[2] * fr.s, BG_VB[3] * fr.s
```

```html
<image href="/bible-map/img/levant-topo.svg"
       x="…" y="…" width="…" height="…" preserveAspectRatio="none"/>
```

`preserveAspectRatio="none"` 이 중요합니다. 이걸 빼면 브라우저가 제멋대로 비율을 맞춰서 **점과 배경이 어긋납니다.**

### 3-3. 도성 지도 — 격자가 없으면 랜드마크로 역산한다

고난주간(7국면)은 예루살렘 성 안이 무대입니다. 지역 지도로는 1픽셀이 60~220m라 아무것도 구분되지 않아 별도의 도성 지도를 씁니다. 그런데 이 지도에는 **위경도 격자선이 없습니다.**

해법: 좌표를 아는 랜드마크(성전 산, 다마스커스 문, 시온 문, 감람산 등) 몇 곳의 픽셀 위치를 읽어 **아핀 변환을 역산**했습니다. 결과가 이 두 줄입니다.

```python
def sx(lat,lon): return  72911.7*lon + 1296.4*lat - 2609444.8
def sy(lat,lon): return    302.0*lon - 88846.8*lat + 2813613.8
```

계수의 뜻을 읽어 보면 검산이 됩니다. `72911.7 / 88846.8 ≈ 0.82` — 이 위도(북위 31.8°)에서 경도 1도의 실제 거리는 위도 1도의 `cos(31.8°) ≈ 0.85`배입니다. 대략 맞습니다. 그리고 `1296.4`와 `302.0`은 작은 값인데, 이는 원본 지도가 **정북을 향해 살짝 기울어져 있다**는 뜻입니다.

> **교훈** — 계수를 얻은 뒤 「이 숫자가 물리적으로 무슨 뜻인가」를 한 번 따져 보세요. 부호가 뒤집혔거나 자릿수가 틀린 실수를 여기서 대부분 잡습니다.

## 4. 핵심 기술 ② 배경 SVG 손질 (`optimize_svg.py`)

위키미디어 지도는 웹에 그대로 올릴 수 없습니다. 두 가지 이유입니다.

1. **무겁다** — 원본 7.8MB. 방문자마다 이걸 내려받게 할 수는 없습니다.
2. **남의 글씨가 있다** — 영문·독문 지명, 격자 눈금, 고도 범례. 우리는 한글 지명을 그 위에 얹으므로 원래 글씨는 방해가 됩니다.

`optimize_svg.py`는 선언적 목록 하나로 두 지도를 처리합니다.

```python
MAPS = [
    dict(src="Southern_Levant_blank_topographic_map.svg", dst="levant-topo.svg",
         author="DEGA MD", license="CC BY-SA 4.0",
         # 격자·눈금자·고도범례에 글씨가 들어 있다. 지형만 남긴다.
         drop=["gridline", "scalebar", "elevation-legend", …]),
    dict(src="Map_of_the_Old_City_and_surroundings_of_Jerusalem.svg", dst="jerusalem-oldcity.svg",
         author="Obendorf", license="CC BY-SA 3.0",
         # 글씨·기호가 외곽선 path로 변환돼 있어 <text>로는 찾을 수 없다.
         drop=["#g356", "#g254"]),
]
```

### 처리 순서가 중요하다

```text
1) 레이어 제거      ← inkscape:label 로 찾는다
2) 편집기 메타데이터 제거
3) 좌표 정밀도 축소
4) 출처를 <desc>로 남김
```

**1과 2를 바꾸면 아무 레이어도 지워지지 않습니다.** 메타데이터를 먼저 지우면 `inkscape:label`이 사라져 레이어를 찾을 수 없기 때문입니다(→ [이슈 5](#이슈-5-레이어가-0개-지워짐)).

### 결과

| 파일 | 원본 | 손질 후 | 전송량(brotli) |
|---|---|---|---|
| `levant-topo.svg` | 7.80 MB | **5.47 MB** (−30%) | 1.74MB → **986 KB** (−44%) |
| `jerusalem-oldcity.svg` | 464 KB | **31 KB** (−93%) | **5.4 KB** |

도성 지도가 93% 줄어든 것은 글씨 644개 path가 파일의 대부분이었기 때문입니다.

> 지형도가 여전히 5.47MB인 것은 **등고선 자체가 데이터**라서 그렇습니다. 이건 줄일 수 없는 부분입니다. Cloudflare가 brotli로 압축해 986KB로 전송하고, 8개 지도가 같은 파일 하나를 공유하며 브라우저가 캐시하므로 실제 부담은 첫 방문 1회입니다.

## 5. 핵심 기술 ③ 공용 엔진 `mapkit.py`

**처음에는 국면마다 생성기를 통째로 복사했습니다.** 1국면(`gen_map_birth.py`)을 만들고, 2국면을 만들려니 좌표 변환·HTML 템플릿·성구 인용·교재 렌더가 전부 똑같았습니다. 그대로 두면 8개 파일에 같은 코드가 8벌 생기고, 버그를 고칠 때 8곳을 고쳐야 합니다.

그래서 2국면 작업 시작 시점에 **공통 부분을 `mapkit.py`로 뽑아냈습니다.**

```text

   ├ verse()          성경 DB 인용
   ├ bible_url()      성서공회 링크
   ├ sx() sy() Frame  좌표 변환 · 잘라내기
   ├ build_map()      지도 HTML 생성

   ├ PLACES   장소: 이름·위경도·분류·설명·이름표 위치
```

이 구조의 값어치는 **9국면을 추가할 때 드러납니다.** `phase_i.py` 하나만 쓰면 지도·교재·목차·네비게이션이 전부 따라옵니다.

## 6. 핵심 기술 ④ 배치 자동 검사 — 이 프로젝트의 가장 유용한 장치

지도 생성에서 가장 자주 나는 실수는 **이름표가 겹치는 것**과 **점이 화면 밖으로 나가는 것**입니다. 눈으로 확인하면 놓칩니다. 8개 지도 × 4~13개 장소를 매번 눈으로 볼 수는 없습니다.

그래서 `_check_layout()`이 문제를 찾으면 **생성 자체를 실패시킵니다.**

```python
def _check_layout(places_out, geo):
    """표시가 캔버스를 벗어나거나 라벨이 다른 점과 겹치면 생성을 멈춘다."""
    bad = []
    # ① 점이 캔버스 밖
    for p in places_out.values():
        if not (0 <= p["x"] <= W and 0 <= p["y"] <= H):
            bad.append(f'{p["name"]} 점이 캔버스 밖 ({p["x"]:.0f},{p["y"]:.0f})')
    # ② 이름표가 다른 장소의 점을 덮음 (32px 이내)
    # ③ 이름표끼리 겹침 — 한글 한 자를 약 15px로 보고 사각형으로 견준다
    # ④ 지형 라벨(「갈릴리」 「유대」)이 밖으로 나가거나 점·이름표를 덮음
    if bad:
        raise SystemExit("배치 문제:\n   - " + "\n   - ".join(bad))
```

여기에 `Frame.fit()`이 하나 더 있습니다. 잘라낸 범위 밖에 장소가 있으면 **어느 방향으로 얼마나 벗어났는지** 알려 줍니다.

```python
raise SystemExit("장소가 잘라낸 범위를 벗어납니다: "
                 "경도 34.870~35.990 (틀 34.230~36.580)")
```

### 이 검사가 실제로 잡은 것

검사기는 **10건 이상의 실제 결함**을 잡았습니다. 그중 몇 가지:

```text
배치 문제:
   - 갈 릴 리 가 게네사렛 이름표와 겹침          (4국면)
   - 갈 릴 리 가 디베랴 바다 이름표와 겹침        (8국면)
   - 유 대 가 엠마오 길 이름표와 겹침            (8국면)
   - 벳새다 라벨이 가버나움 점과 겹침            (4국면)
```

검사기 ④(지형 라벨)는 **나중에 추가한 것**인데, 추가한 즉시 이미 만들어 둔 지도에서 3건을 찾아냈습니다. 즉 그때까지 나는 잘못된 지도를 만들고 있었고 모르고 있었습니다.

> **교훈** — 「눈으로 보면 알 수 있는 문제」야말로 자동 검사로 넘겨야 합니다. 사람의 눈은 8번째 지도에서 반드시 지칩니다. 그리고 검사를 **경고가 아니라 실패로** 만드세요. 경고는 무시됩니다.

여기부터가 이 문서의 핵심입니다. **잘된 결과보다 잘못된 과정에서 배울 것이 많습니다.**

### 이슈 1. 지도가 지리적으로 틀림 ★가장 중요★

#### 현상
1국면(탄생과 유년기) 지도를 처음 만들었을 때, 사용자가 이렇게 지적했습니다.

> 「'탄생, 유년기'의 지도가 이상하게 표현되었어. **베들레헴과 예루살렘이 요단강 동편**에 표시되어 있어.」

성경 지도에서 이건 치명적입니다. 베들레헴과 예루살렘은 요단강 **서편**입니다.

#### 원인
처음 배경으로 쓴 것은 **직접 그린 일러스트 SVG**였습니다. 지형은 「대충 이런 모양」으로 그렸고, 지명 점은 「대충 이 근처」에 손으로 배치했습니다. 기준이 없으니 오차가 누적되어 강 하나를 건너가 버렸습니다.

**근본 원인은 「좌표계가 없었다」는 것입니다.** 눈대중은 언제나 틀립니다.

#### 해결
사용자가 위키미디어의 실제 지형도를 직접 찾아 제공했고, 접근을 완전히 바꿨습니다.

1. **실측 지형도**를 배경으로 사용
2. 원본 격자에서 **좌표 변환식을 역산** (3-1절)
3. 모든 장소를 **실제 위경도**로 지정 — 「베들레헴 = 31.7054, 35.2024」
4. 애굽처럼 축척 밖의 장소는 **화살표 방향 표시**로 처리 (사용자 제안)

```python
"bethlehem": dict(name="베들레헴", lat=31.7054, lon=35.2024, …)
```

이제 점의 위치는 **계산 결과**입니다. 사람이 개입할 여지가 없으므로 틀릴 수 없습니다.

#### 교훈
- **지도에서 「보기 좋게」와 「정확하게」가 부딪히면 정확한 쪽을 택해야 합니다.** 보기 좋은 거짓 지도는 교육 자료로서 가치가 음수입니다.
- 조정이 필요하면 **이름표만 옮기고 점은 그대로 두세요.** 그래서 `lab=(-72, -18)` 같은 이름표 offset과 연결선(leader line)을 따로 만들었습니다.
- 사용자가 「지도가 이상하다」고 한 것은 **결과물을 실제로 본 사람만 할 수 있는 지적**입니다. 만든 사람은 자기 코드가 의도대로 돌았다는 것만 확인하고 넘어가기 쉽습니다.

### 이슈 2. 출처 URL과 실제 파일이 다름

#### 현상
사용자가 「이 사이트에서 다운받았다」며 위키미디어 URL을 알려 줬는데, 실제 저장된 파일명이 URL의 파일명과 달랐습니다. 한 번은 파일명을 잘못 알려 준 것을 사용자가 직접 정정했습니다.

#### 원인
위키미디어 공용에는 **비슷한 지도가 여러 개** 있고, 서로 저작자와 라이선스 버전이 다릅니다. URL을 그대로 믿고 표기하면 **엉뚱한 사람에게 저작자 표시를 하게 됩니다.**

#### 해결
알려 준 URL을 믿지 않고, **실제 파일마다 해당 Commons 페이지를 직접 확인**했습니다. 결과:

| 파일 | 저작자 | 라이선스 |
|---|---|---|
| Southern Levant blank topographic map | DEGA MD | CC BY-SA **4.0** |
| Map of the Old City … Jerusalem | Obendorf | CC BY-SA **3.0** |

버전까지 다릅니다. 3.0과 4.0은 조항이 다르므로 뭉뚱그릴 수 없습니다.

#### 교훈
- **저작권 표기는 「대충」이 허용되지 않는 영역입니다.** 잘못된 표기는 표기 없음보다 나쁠 수 있습니다.
- 파일과 출처 페이지를 **1:1로 대응시켜 기록**해 두세요. `_sources/maps/README.md`가 그 역할을 합니다.

### 이슈 3. CC BY-SA의 ShareAlike가 성경공부 본문까지 전염되는가?

#### 질문
CC BY-SA는 **동일조건변경허락**입니다. 「이 지도를 쓰면 우리 성경공부 교재도 CC BY-SA로 풀어야 하나?」

#### 판단
아닙니다. ShareAlike는 **원저작물을 변경한 결과물(adaptation)** 에 적용됩니다.

| 대상 | ShareAlike 적용 |
|---|---|
| 손질한 배경 지도(`levant-topo.svg`) | **적용** — 원본의 2차적 저작물 |
| 그 지도 위의 점·이름표를 포함한 **지도 전체** | **적용** |
| 같은 페이지에 나란히 있는 **성경공부 본문** | **미적용** — 독립 저작물(collection) |

즉 지도는 CC BY-SA로 제공하고, 교재 텍스트는 별개입니다. 다만 이 구분이 독자에게 보이지 않으면 오해를 낳으므로, **지도에만 붙는 크레딧 상자**를 따로 만들어 경계를 분명히 했습니다.

#### 결과 — 표기를 세 곳에 넣었다

1. **지도 화면 안** 크레딧 상자 (링크 포함)
2. **교재 미니지도 캡션** 아래 한 줄
3. **콘텐츠 페이지** 「이 지도에 대하여」 항목

```python
CREDIT = ('배경 지형도: <a href="https://commons.wikimedia.org/…">Southern Levant blank '
          'topographic map</a> © DEGA MD · <a href="…by-sa/4.0/">CC BY-SA 4.0</a> · 변경됨')
```

「**변경됨**」을 반드시 넣습니다. CC BY-SA는 변경 사실 명시를 요구합니다.

### 이슈 4. 지도의 글씨를 지울 수 없다

#### 현상
배경 지도에서 영문 지명을 지우려고 `<text>` 요소를 찾았으나 **하나도 없었습니다.** 그런데 화면에는 글씨가 분명히 보입니다.

#### 원인
Inkscape로 저장할 때 **글씨를 외곽선 path로 변환**(text-to-path)한 파일이었습니다. 글자 하나가 곡선 여러 개로 바뀌어 있어서, XML상으로는 그냥 도형입니다. 텍스트 검색으로는 절대 찾을 수 없습니다.

#### 해결
검색을 포기하고 **그룹 단위로 실험**했습니다. 브라우저에서 파일을 열고 그룹을 하나씩 `display:none`으로 숨긴 뒤 스크린샷을 비교했습니다.

```javascript
document.getElementById('g356').style.display='none'   // → 글씨가 전부 사라짐
document.getElementById('g254').style.display='none'   // → 교회 기호가 사라짐
```

`g356`에 글씨 path 644개, `g254`에 기호가 모여 있었습니다. 이걸 `optimize_svg.py`의 제거 목록에 넣었습니다.

```python
# 글씨·기호가 외곽선 path로 변환돼 있어 <text>로는 찾을 수 없다.
# 확인 결과 g356(글씨 644개 path)·g254(교회 기호)에 모여 있다.
drop=["#g356", "#g254"],
```

#### 교훈
- **찾는 방법이 없으면 방법을 바꾸세요.** 「텍스트를 찾는다」가 막혔을 때 「보이는 것을 하나씩 지워 본다」로 전환한 것이 답이었습니다.
- SVG 작업은 **파일 구조를 실제로 열어 확인**해야 합니다. 「SVG니까 `<text>`가 있을 것」은 추측입니다.

### 이슈 5. 레이어가 0개 지워짐

#### 현상
`optimize_svg.py`를 돌렸는데 「레이어 0개 제거」. 파일 크기도 그대로입니다.

#### 원인
처리 순서가 잘못됐습니다.

```text
잘못된 순서:  ① 메타데이터 제거 (inkscape:* 속성 삭제)
              ② 레이어 제거     (inkscape:label 로 찾음)  ← 이미 지워져서 못 찾음
```

레이어 이름은 `inkscape:label` 속성에 들어 있습니다. 메타데이터 정리에서 `inkscape:*`를 통째로 지워 버리니, 그 다음 단계에서 찾을 이름이 없었습니다.

#### 해결
순서를 뒤집고, 그 이유를 코드 주석에 남겼습니다.

```python
# 1) 레이어 제거를 먼저 — inkscape:label 을 지운 뒤에는 레이어를 찾을 수 없다
# 2) 편집기 메타데이터 제거
# 3) 좌표 정밀도 축소
# 4) 출처를 <desc>로 남김
```

#### 교훈
- **파이프라인의 각 단계가 다음 단계의 입력을 망가뜨리지 않는지** 확인하세요. 「정리」 단계는 특히 위험합니다.
- 「0개 처리됨」이라는 결과를 성공으로 넘기지 마세요. **아무 일도 일어나지 않은 것은 실패입니다.**

### 이슈 5-b. 최적화한 SVG를 브라우저가 거부함

#### 현상
좌표 정밀도를 줄인 뒤 배경 지도가 아예 표시되지 않았습니다.

#### 원인 두 가지

**(1) 전역 반올림이 XML 선언을 깨뜨렸다**

숫자를 줄이는 정규식을 문서 전체에 적용하니 `version="1.0"`이 `version="1"`이 되었습니다. SVG 명세에 없는 값이라 파서가 거부합니다.

**(2) `ElementTree.tostring`은 XML 선언을 붙이지 않는다**

```python
XML_DECL = '<?xml version="1.0" encoding="UTF-8" standalone="no"?>'
# ElementTree.tostring 은 XML 선언을 붙이지 않으므로 직접 되살린다
```

#### 해결
반올림 대상을 **좌표를 담는 속성만**으로 한정했습니다.

```python
COORD_ATTRS = ("d","points","x","y","cx","cy","r","rx","ry","x1","y1","x2","y2",
               "width","height","transform","stroke-width")
```

#### 교훈
**「모든 숫자」를 대상으로 하는 정규식은 거의 항상 너무 넓습니다.** 무엇을 바꿀지 화이트리스트로 명시하세요.

### 이슈 7. 지명을 클릭해도 아무 일도 일어나지 않음 ★교훈이 큰 이슈★

#### 현상
사용자가 보고했습니다.

> 「지도의 지명을 클릭하면 그 장소의 사건 리스트로 이동해야 할 것 같은데 **문제가 있어.**」

지도 확대/이동은 잘 됩니다. 그런데 점을 클릭해도 오른쪽 패널이 바뀌지 않습니다.

#### 원인 — 포인터 캡처의 함정

확대/이동을 매끄럽게 하려고 `pointerdown`에서 즉시 `setPointerCapture()`를 걸었습니다.

```javascript
svg.addEventListener('pointerdown', ev => {
  svg.setPointerCapture(ev.pointerId);   // ← 이 한 줄이 원인
  ...
});
```

`setPointerCapture`는 **이후의 모든 포인터 이벤트를 캡처한 요소로 재타겟팅**합니다. `click`도 포인터 이벤트 계열이므로, 실제로 클릭한 것이 `<circle>`(장소 점)이어도 이벤트는 `<svg>`에 전달됩니다. 자식 요소의 클릭 핸들러는 **한 번도 실행되지 않습니다.** 에러도 나지 않고, 조용히 죽습니다.

부차적 원인이 하나 더 있었습니다. 지명 글씨(`.lbl`)에 `pointer-events:none`이 걸려 있어서, 글씨를 클릭해도 무시됐습니다.

#### 해결
**실제로 끌기가 시작된 뒤에만** 캡처를 걸도록 바꿨습니다. 5px 이상 움직였을 때가 「끌기」입니다.

```javascript
/* 주의: pointerdown에서 setPointerCapture를 걸면 click이 svg로 재타겟팅되어
   점(장소) 클릭 핸들러가 전혀 실행되지 않는다. 실제로 끌기 시작한 뒤에만 캡처한다. */
let capId = null;
svg.addEventListener('pointerdown', ev => { down=true; dragged=false; moved=0; … });
svg.addEventListener('pointermove', ev => {
  if (moved > 5 && !dragged) {
    dragged = true; svg.classList.add('grab');
    try { svg.setPointerCapture(ev.pointerId); capId = ev.pointerId; } catch(e) {}
  }
  if (!dragged) return;
  …
});
```

그리고 이름표와 개수 배지도 클릭 대상으로 만들었습니다(`cursor:pointer`, `pointer-events` 제거).

#### 교훈 — 검증 방법이 버그를 숨겼다

이 버그가 사용자에게 발견될 때까지 남아 있던 이유가 중요합니다.

나는 클릭 동작을 **`dispatchEvent`로 검증했습니다.**

```javascript
document.querySelector('#place-bethany').dispatchEvent(new MouseEvent('click'))
// → 패널이 정상적으로 바뀜. "잘 되는군" ✅
```

`dispatchEvent`로 만든 이벤트는 **포인터 캡처를 거치지 않습니다.** 그래서 통과합니다. **실제 마우스 클릭만 실패합니다.**

> **이것이 이 프로젝트에서 배운 가장 값진 교훈입니다.**
> **사용자 입력을 코드로 재현해 검증하면, 브라우저의 입력 처리 계층에서 생기는 버그를 구조적으로 놓칩니다.** 클릭·터치·드래그는 실제 마우스로 확인해야 합니다.

### 이슈 8. 구절 표기가 「마 마 21:1-11」로 중복됨

#### 현상
사건 카드의 구절 칩에 책 이름이 두 번 나왔습니다.

#### 원인
병행 구절을 담은 딕셔너리가 이런 모양입니다.

```python
{"마": "마 21:1-11", "막": "막 11:1-11"}
```

**키에도 값에도 책 약칭이 있습니다.** 렌더링할 때 `키 + " " + 값`으로 이었으니 「마 마 21:1-11」이 됐습니다.

```javascript
function refsHtml(refs){   // 값에 이미 책 약칭이 있어 키(b)를 덧붙이지 않는다 (‘마 마 21:1’ 방지)

}
```

#### 교훈
데이터 구조를 만들 때 **같은 정보를 두 곳에 두지 마세요.** 키를 「마태복음」으로 하거나 값을 「21:1-11」로 했다면 이 버그는 생길 수 없었습니다.

### 이슈 9. 예루살렘 안의 사건들이 한 점으로 뭉침 ★설계 판단★

#### 현상
5국면(유대 사역)과 8국면(부활과 승천)에서 성전·실로암 못·다락방·빈 무덤·감람산이 **거의 같은 자리**에 겹쳤습니다. 이름표가 서로를 덮어 읽을 수 없습니다.

#### 원인
축척의 물리적 한계입니다. 지역 지도는 1도 = 500px이므로 **1px ≈ 60~220m**입니다. 성전과 실로암 못은 실제로 800m, 빈 무덤과 감람산은 1.5km 거리입니다. 지도에서 4~25px 차이입니다. 이름표(가로 60~100px)가 겹치지 않을 방법이 없습니다.

#### 시도 1 — 확대 삽도 (실패)

유대 지역만 확대한 작은 삽도를 만들어 옆에 붙이고 실제 위치와 점선으로 연결했습니다.

**결과: 더 나빠졌습니다.** 삽도가 요단강 동편 여백에 놓였는데, 삽도 자체가 지도처럼 보여서 **베들레헴과 예루살렘이 요단 동편에 있는 것처럼 읽혔습니다.** 이슈 1과 똑같은 오해를 다른 방식으로 만든 것입니다. 삽도는 완전히 제거했습니다.

#### 시도 2 — 노드 병합 (채택)

축척에서 구분할 수 없는 지점들을 **하나의 장소로 합치고, 그 사실을 명시**했습니다.

```python
# 이 틀에서 1px ≈ 100m다. 빈 무덤·다락방·감람산은 1.5km 안쪽이라 한 점으로 뭉치므로
# '예루살렘 일대'로 합쳤다. 성내 세부 위치는 고난주간 지도에서 볼 수 있다.
"jerusalem": dict(name="예루살렘 일대", lat=31.7770, lon=35.2340, …,
  desc="빈 무덤(부활 아침)과 다락방(나타나심·도마의 고백), 그리고 감람산(승천)이 "
       "모두 이 성과 그 동편에 있다."),
```

그리고 콘텐츠 페이지에 **한계를 그대로 적고, 대안을 안내**했습니다.

```markdown
- 빈 무덤·다락방·감람산은 1.5km 안쪽이라 이 축척에서 한 점으로 뭉치므로
  **'예루살렘 일대'로 합쳤습니다**.
- 성내 세부 위치는 [🁢 7. 고난주간](/bible-map/passion-week/) 지도에서 도성 규모로
  볼 수 있습니다.
```

도성 규모가 필요한 고난주간은 **아예 다른 지도**(예루살렘 구시가 지도)를 씁니다. 축척이 다른 문제는 축척이 다른 지도로 푸는 것이 정답입니다.

#### 교훈
- **한계를 숨기지 말고 표시하세요.** 「이 축척에서는 구분되지 않습니다 + 여기서 보세요」가 억지로 떼어 놓은 것보다 정직하고 유용합니다.
- **거리를 거짓으로 만드는 시각적 편의는 채택하지 마세요.** 삽도는 보기엔 좋았지만 지리를 왜곡했습니다.
- 5국면에서는 갈릴리를 지도 범위 밖으로 빼고 **방향 표시**로 처리했습니다. 하나를 넣기 위해 나머지 전부를 작게 만드는 것은 손해입니다.

### 이슈 13. 저작자 표기가 다른 파일을 가리키고 있었다 ★이 문서를 쓰다가 발견★

#### 현상
**이 보고서를 작성하면서** 발견한 결함입니다. 1국면(탄생과 유년기) 콘텐츠 페이지의 「이 지도에 대하여」 항목이 배경 지도를 이렇게 표기하고 있었습니다.

```markdown
- **배경 지도 출처**: [The Ministry of Jesus](…File:The_Ministry_of_Jesus.svg) © DEGA MD …
```

그런데 **1국면 지도가 실제로 불러오는 파일은 `levant-topo.svg`** = 『Southern Levant blank topographic map』입니다. 페이지가 쓰지 않는 파일을 출처로 적고 있었습니다.

#### 원인
작업 순서가 남긴 흔적입니다.

```text
① 처음: 지명이 표시된 The_Ministry_of_Jesus.svg 를 배경으로 사용 → 페이지에 출처 표기

③ 그런데 ①에서 쓴 출처 문장은 그대로 남았다
```

지도 화면 안의 크레딧 상자와 교재 미니지도 캡션은 `mapkit.py`가 **코드에서 생성**하므로 자동으로 맞게 바뀌었습니다. 반면 콘텐츠 페이지의 그 한 줄만 **손으로 쓴 마크다운**이어서 갱신되지 않았습니다. 다른 7개 국면은 `gen_pages.py`가 생성하므로 처음부터 정확했고, **1국면만 틀렸습니다.**

#### 해결
실제 사용 파일로 정정하고, 좌표 검증에 쓴 지명 표기판은 그 역할대로 따로 언급했습니다.


## 9. 인쇄·PDF — 종이로 쓰는 교재 만들기

교재는 화면으로 읽는 글이 아니라 **인쇄해서 손으로 쓰는 자료**입니다. 그런데 처음 만들 때는 화면만 보고 만들었고, 사용자가 실제로 인쇄해 보고서야 문제가 드러났습니다.

| 용량 | 2.5MB | 3.7MB |
| 용지 | Letter | Letter *(한국은 A4)* |
| 배경 | 전면 베이지 | 여백 베이지 + 카드 그림자 |

교재 CSS를 확인하니 **`@media print` 규칙이 한 줄도 없었습니다.** 네 곳의 CSS 사본(`mapkit.py`·`gen_study.py`·`gen_study_birth.py`·`booklib.py`) 모두 0개. 화면용 스타일이 그대로 종이로 넘어가고 있었습니다.

### 이슈 15. 배경을 끄면 필기줄도 사라진다 ★인쇄 문제의 핵심★

#### 현상
브라우저 인쇄 설정에는 「배경 그래픽」 옵션이 있습니다. 이걸 **끄면** 베이지 바탕은 사라지는데 **필기줄도 함께 사라집니다.** **켜면** 필기줄은 나오지만 베이지가 온 지면을 덮습니다. 어느 쪽도 쓸 수 없는 상태였습니다.

#### 원인
필기줄을 **CSS 배경 이미지**로 그렸기 때문입니다.

```css
.write{background:repeating-linear-gradient(transparent 0 32px,var(--rules) 32px 33px)}
```

`repeating-linear-gradient`는 이름이 그라디언트지만 **배경 이미지**입니다. 「배경 그래픽 끄기」는 배경색과 배경 이미지를 함께 끄므로, 베이지 바탕과 필기줄이 같은 스위치에 묶여 있었습니다.

#### 해결
필기줄을 **테두리**로 바꿨습니다. 테두리는 배경이 아니라 요소의 일부이므로 「배경 그래픽 끄기」와 무관하게 항상 인쇄됩니다.

```css
/* 필기줄 — 배경 이미지가 아니라 테두리다. '배경 그래픽 끄기'에도 살아남는다. */
.write{margin:.3em 0 1em}
.write i{display:block;height:32px;border-bottom:1px solid var(--rules)}
@media screen{.write i.px{display:none}}   /* 세 번째 줄은 종이에서만 */
```

```python
# 세 번째 줄은 인쇄에서만 보인다(.px) — 종이에는 손으로 쓸 자리가 더 필요하다
WRITE = '<div class="write"><i></i><i></i><i class="px"></i></div>'
```

곁들여 얻은 것이 하나 있습니다. 화면은 2줄, 종이는 3줄로 **매체마다 다르게** 줄 수를 줄 수 있게 됐습니다. 화면에서 3줄은 낭비고, 종이에서 2줄은 부족합니다.

#### 교훈
- **「보이는 선」을 배경으로 그리지 마세요.** 배경은 사용자가 끌 수 있는 것이고, 테두리는 내용의 일부입니다. 필기줄은 내용입니다.
- 인쇄 설정의 스위치 하나에 **성격이 다른 두 요소가 묶이지 않도록** 하세요.

### 이슈 16. 다크 모드가 종이로 넘어간다

#### 현상
맥이 다크 모드일 때 인쇄하면 **검은 바탕에 흰 글씨**가 나옵니다. 토너를 지면 전체에 붓습니다.

#### 원인
`@media (prefers-color-scheme:dark)`가 **인쇄에도 적용됩니다.** 인쇄는 별개의 매체지만, 색 구성 선호는 기기 설정이므로 그대로 따라옵니다.

#### 해결
`@media print`에서 색 토큰을 되돌립니다. **다크 모드 규칙보다 뒤에 두어야** 우선순위에서 이깁니다.

```css
@media print{
 :root{--paper:#fff;--card:#fff;--ink:#111;--soft:#333;--muted:#585858;
  --rule:#c9c9c9;--rules:#b3b3b3;--tint:#fff;--accent:#7d5c22;--accentd:#5c4319}
 @page{size:A4;margin:14mm 15mm}        /* 한국 기본 용지 */
 .page{max-width:none;border:0;border-radius:0;box-shadow:none;padding:0}
 .step,.panel,.ev,figure.map,blockquote{break-inside:avoid}   /* 문항이 갈라지지 않게 */
 .sh,.eyebrow,h1.title,.q{break-after:avoid}
 .tools,.lnav{display:none!important}   /* 단추·네비는 종이에 쓸모없다 */
}
```

#### 교훈
**CSS 변수로 색을 다루면 이런 되돌리기가 한 블록으로 끝납니다.** 색을 규칙마다 직접 써 놓았다면 수십 곳을 고쳐야 했습니다.

### 이슈 17. 흑백 필터가 PDF를 6배로 키운다 ★뜻밖의 인과관계★

#### 현상
잉크를 아끼려고 지도에 흑백 필터를 걸었습니다.

```css
.minimap{max-height:105mm;filter:grayscale(1) contrast(1.06)}
```

그런데 한 과가 **1.3MB**가 됐습니다. 78과면 100MB입니다.

#### 원인
PDF 안을 들여다보니 **2125×1435 무손실 비트맵이 두 장**(789KB) 들어 있었습니다.

```text
이미지 XObject:  2125x1435  FlateDecode
                2125x1435  FlateDecode
```

CSS 필터는 벡터로 표현할 수 없습니다. 그래서 Chrome이 **필터를 적용한 결과를 비트맵으로 구워** 넣습니다. 무손실(FlateDecode)이라 JPEG보다 5배쯤 큽니다.

필터를 빼 보니 **더 나빠졌습니다 — 3.8MB.** 이번에는 지형 SVG의 벡터 경로(5.5MB짜리)가 통째로 들어갔습니다.

| 방식 | 한 과 크기 | 무엇이 들어갔나 |
|---|---|---|
| 흑백 필터 | 1,323KB | 무손실 비트맵 2장 |
| 필터 없음 | **3,779KB** | 지형 SVG 벡터 경로 |
| 흑백 + 지도 축소 | 1,062KB | 조금 작은 비트맵 |

#### 해결 — 배경을 미리 래스터로 굽는다

두 방법이 다 나쁜 이유는 같습니다. **교재 미니지도에 5.5MB짜리 벡터 지도를 쓰고 있다는 것.** 미니지도는 확대하지 않으므로 벡터일 이유가 없습니다.

국면별로 **잘라낸 그림 그대로** JPEG을 미리 구웠습니다(`gen_terrain.py`). 확대·이동이 필요한 인터랙티브 지도는 그대로 벡터를 씁니다.

```python
OUTW, OUTH = 1500, 1020    # 미니지도 최대 표시 폭의 약 3배 — 인쇄 300dpi에 충분
QUALITY = 62               # 지형도는 완만한 색면이라 낮은 품질에도 잘 버틴다
```

이미 잘려 있으므로 미니지도는 캔버스를 그대로 채우면 됩니다 — 좌표 계산이 사라집니다.

```python
if raster:
    bgx, bgy, bgw, bgh = 0, 0, W, H
    bg_href = f'/bible-map/img/terrain-{ph["slug"]}.jpg'
```

그리고 흑백 필터는 **뺐습니다.** JPEG에 필터를 걸면 다시 무손실 비트맵으로 구워지기 때문입니다. 흑백은 프린터의 「흑백 인쇄」 설정으로 하면 됩니다.

| | 이전 | 이후 |
|---|---|---|
| 한 과 PDF | 1,323KB | **806KB** |
| PDF 안의 지도 | 무손실 비트맵 2장 | **JPEG 1장** (DCTDecode, 214KB) |
| 교재 8개 래스터 | — | 94~274KB, 합계 1.6MB |
| 화면에서 미니지도용 내려받기 | 986KB (SVG, brotli) | **~200KB** (JPEG) |

마지막 줄이 뜻밖의 이득입니다. 교재를 열 때마다 5.5MB SVG를 받고 있었는데, 이제 200KB만 받습니다.

#### 교훈
- **CSS 필터는 벡터를 비트맵으로 바꿉니다.** `filter`, `opacity`가 걸린 그룹, `mix-blend-mode`, 둥근 모서리 클립 — 모두 래스터화를 유발합니다. 인쇄물에서는 용량과 화질에 직결됩니다.
- **용량 문제는 짐작하지 말고 PDF 안을 열어 보세요.** 「이미지 XObject의 크기와 필터 종류」만 보면 원인이 바로 나옵니다.

```python
for m in re.finditer(rb'/Subtype\s*/Image(.{0,400}?)stream', d, re.S):
    ...  # /Width /Height /FlateDecode(무손실) vs /DCTDecode(JPEG)
```

- **같은 자료라도 쓰임에 따라 형식을 나누세요.** 확대하는 지도는 벡터, 고정 크기 미니지도는 래스터. 하나로 통일하려는 욕심이 양쪽을 망칩니다.

### 이슈 18. 78개 PDF의 대부분은 한글 폰트다

```python
def page_of(html: str) -> str:
    """교재 HTML에서 본문 <div class="page"> … </div> 만 떼어 낸다.
    단추(.tools)와 과 이동 네비(.lnav)는 종이에 쓸모가 없어 뺀다."""
```


### 이슈 19. headless Chrome이 PDF를 다 쓰고도 끝나지 않는다

#### 현상
`--print-to-pdf`로 PDF를 굽는 스크립트가 120초 타임아웃에 걸립니다. 그런데 **PDF 파일은 완성되어 있습니다**(1323KB, 4쪽, 정상).

#### 원인
Chrome 150에서 `--print-to-pdf`와 `--screenshot` 모두 출력을 마친 뒤 프로세스가 종료되지 않습니다. `--headless=old`, `--headless=new`, `--virtual-time-budget` 세 가지를 다 시험했지만 결과가 같았습니다.

```text
  headless=old           TIMEOUT   70.0초  1323KB
  headless=new           TIMEOUT   70.0초  1323KB
  old+vtb                TIMEOUT   70.0초  1323KB
```

#### 해결
**프로세스가 끝나기를 기다리지 않고, 결과 파일의 크기가 멈추면** 완성으로 보고 직접 종료시킵니다.

```python
while time.time() < deadline:
    if proc.poll() is not None:      # 스스로 끝났으면 그대로 둔다
        break
    size = dst.stat().st_size if dst.exists() else 0
    if size and size == last:
        stable += 0.4
        if stable >= 1.2:            # 1.2초간 크기가 그대로면 완성
            break
    else:
        stable = 0.0
    last = size
    time.sleep(0.4)
```

#### 교훈
- **외부 도구는 문서대로 동작하지 않을 수 있습니다.** 버전과 플래그를 바꿔 세 번 시험해 보고 안 되면, 도구를 고치려 하지 말고 **관찰 가능한 결과**(파일 크기)를 기준으로 삼으세요.
- macOS에는 `timeout` 명령이 없습니다(coreutils의 `gtimeout`). 셸에서 `timeout`을 쓰면 종료코드 127이 납니다.

## 11. 설계 원칙 정리 — 다른 프로젝트에 옮길 것들

이 프로젝트에서 얻은 원칙을 일반화하면 이렇습니다.

### ① 눈대중을 계산으로 바꾼다
손으로 배치한 것은 반드시 틀립니다. 위경도 → 픽셀 변환식을 세우고 나면 **틀릴 수가 없습니다.** 사람이 개입하는 지점을 최소화하세요.

### ② 눈으로 확인하던 것을 검사기로 만든다
「이름표가 겹치나?」는 사람이 보면 알지만 8번째 지도에서 지칩니다. `_check_layout()`이 10건 이상을 잡았습니다. **경고가 아니라 실패로** 만드세요.

### ③ 복사 두 번째에 공통부를 뽑는다
1국면 생성기를 2국면에 복사할 때가 `mapkit.py`를 만들 시점이었습니다. 세 번째 복사까지 기다리면 이미 늦습니다. 지금은 **데이터 파일 하나로 국면이 추가**됩니다.

### ④ 정확한 인용은 원본 DB에서만 꺼낸다
성경 본문을 기억으로 쓰지 않습니다. 참조 구절은 본문을 복제하지 않고 **공식 사이트로 링크**합니다. 저작권과 정확성을 한 번에 해결합니다.

### ⑤ 저작권은 파일 단위로 확인해 기록한다
알려 준 URL을 믿지 말고 실제 파일의 출처 페이지를 확인하세요. 저작자·라이선스 버전·변경 사실을 **결과물이 보이는 모든 곳**에 표기합니다.

### ⑥ 한계는 숨기지 말고 표시한다
「이 축척에서는 구분되지 않습니다. 여기서 보세요」가 억지로 벌려 놓은 것보다 낫습니다. **거짓 정확도보다 정직한 한계가 유용합니다.**

### ⑦ 사용자 입력은 실제 입력으로 검증한다
`dispatchEvent`는 포인터 캡처를 건너뛰므로 클릭 버그를 숨겼습니다. 클릭·터치·드래그는 **실제 마우스로** 확인하세요.

### ⑧ 원본과 산출물의 저장소를 분리한다
원본은 보관(`_sources/`), 산출물은 배포(`static/`). 섞이면 11MB 파일이 매 배포마다 따라다닙니다.

### ⑨ 셀 수 있는 것은 센다
요약의 숫자는 프로그램으로 확인하세요. 「92과」와 「78과」의 차이는 신뢰의 차이입니다.

### ⑩ 매체가 다르면 스타일도 다르다
화면과 종이는 다른 매체입니다. 화면용 스타일을 그대로 인쇄하면 배경색이 지면을 덮고, 다크 모드가 종이로 넘어옵니다. **인쇄해서 쓰는 자료라면 `@media print`는 선택이 아니라 필수입니다.** 그리고 「보이는 선」은 배경이 아니라 테두리로 그리세요 — 배경은 사용자가 끌 수 있습니다.

### ⑪ 용량 문제는 열어 보고 고친다
PDF가 크다고 내용을 줄이는 것은 대개 헛수고입니다. 실제 원인은 CSS 필터가 유발한 무손실 비트맵(789KB)과 한글 폰트 서브셋(550KB)이었습니다. **파일 안을 열어 무엇이 자리를 차지하는지 세어 보세요.**

### ⑫ 사실을 가리키는 문장은 코드가 쓰게 한다
출처·라이선스·경로·버전 표기를 손으로 쓰면 재료가 바뀔 때 낡습니다. 이 프로젝트에서 자동 생성된 크레딧 세 곳은 전부 맞았고, **손으로 쓴 한 곳만 틀렸습니다**(→ 이슈 13). 사람이 쓸 것은 판단과 설명이고, 사실 대조는 기계의 몫입니다.

## 12. 남은 일 · 확장 방향

### 즉시 가능
- **9국면 추가** — `phase_i.py` 하나 작성. `mapkit.build(PHASE)`가 나머지를 처리합니다.
- **전체 개관 지도** — 8국면 전체를 한 지도에 놓고 시간 순으로 여정 전체를 따라가는 화면.

### 자료가 필요
- **사도행전 전도 여행** — 같은 구조로 바울의 1~3차 여행 + 로마 항해. 배경 지도는 지중해 전역이 필요하므로 새 지형도를 구해 좌표 변환을 다시 역산해야 합니다.
- **출애굽 경로** — 학자 간 경로 이견이 크므로, 복수 견해를 함께 표시하는 설계가 필요합니다.

### 개선 여지
- 지형도 5.47MB — 등고선을 단순화(topology-preserving simplification)하면 더 줄 수 있으나 지형의 정확도를 해칩니다. 현재는 캐시에 의존하는 것이 합리적입니다.
- 골고다·동산 무덤 위치를 성묘교회 전승에서 「가든 툼」 견해로 바꾸는 문제 — 신학적 판단이 필요합니다.
